# Generic ACP agent support: known-agent catalog + "configure your own", and who implements `jetbrains.air`

Date: 2026-11-23
Question: (A) What would it take to turn hoa's Cursor support into a generic ACP agent feature, combining a built-in catalog of known agents with user-configured agents? (B) Which agents listed at <https://agentclientprotocol.com/get-started/agents> implement the JetBrains AIR (`_meta.jetbrains.air`) ACP extensions?

Related: [`2026-11-18-acp-jetbrains-air-capabilities.md`](./2026-11-18-acp-jetbrains-air-capabilities.md) (what the AIR extensions are), [`2026-10-04-acp-terminal-auth-xterm-effect-terminal.md`](./2026-10-04-acp-terminal-auth-xterm-effect-terminal.md) (terminal auth UI), [`2026-10-29-orca-t3code-acp-gemini-antigravity.md`](./2026-10-29-orca-t3code-acp-gemini-antigravity.md).

## Summary

**A. Generic ACP agents.**

- **There is an official catalog to consume, and hoa already consumes it for one agent.** The ACP Registry (`agentclientprotocol/registry`, stabilized) publishes `https://cdn.agentclientprotocol.com/registry/v1/latest/registry.json`. Today it lists 46 agents, each with `id`, `name`, `version`, `description`, `icon`, and a `distribution` of `binary` / `npx` / `uvx` (each with `cmd`/`package`, `args`, `env`). hoa already reads the Antigravity entry (`libs/ui/src/host/antigravityRegistry.ts:9-26`, ADR 0017). Zed, JetBrains, and several desktop clients install agents from it. Hand-maintaining a list is not necessary.
- **The registry weakens the premise that "Cursor needs no runtime."** The registry ships Cursor as a **binary download**: `downloads.cursor.com/.../agent-cli-package.tar.gz`, run as `./dist-package/cursor-agent acp`. hoa instead runs the user's PATH `cursor-agent`. Any agent can be reached either way: a managed download or a CLI on PATH.
- **Prior art for "configure your own" is one shape everywhere: `{ command, args, env }`.**
  - Zed: `agent_servers.<name> = { type: "custom", command, args, env, default_mode, default_config_options, favorite_config_option_values }`, plus `type: "registry"` for installed registry agents.
  - JetBrains: `~/.jetbrains/acp.json` `agent_servers.<display name> = { command, args, env }`, plus `default_mcp_settings`.
- **The hard constraints in hoa are structural, not protocol:**
  1. `AgentLaunchTarget` is a closed 4-member union used as the key of exhaustive `Record<AgentLaunchTarget, …>` maps (quirks, meta, icons, import state). Dynamic agents need data-driven lookup with a default quirk set.
  2. The Tauri capability file allowlists spawnable commands by name and HTTP URLs by exact string. An arbitrary user command or registry archive needs a constrained native spawn, like the existing `spawn_antigravity_provider`, not a wider shell scope.
  3. Auth is per-vendor CLI probes (`vendorCliAuth.ts`). A generic agent must use ACP `authMethods` (`agent` / `terminal` / `env_var`) instead. hoa already parses `authMethods` but drops `type`, and only calls `authenticate` for Antigravity.
- **Capability gating mostly already exists.** `agentCapabilitiesFrom` reads `initialize` once and the Harness/UI gate fork, resume, close, archive, rename, image, and steering on it. A generic agent needs a "no quirks" default, and the remaining hard-coded provider tables (`providerCapabilities`, `PROVIDER_META`, `HIDDEN_COMMAND_NAMES`) must tolerate a missing entry.
- **Proposal** (see [Proposed design](#proposed-design-proposal)): one `AgentDefinition` record with `source: 'builtin' | 'registry' | 'custom'` and `launch: Path | Managed(registry distribution)`. The four built-ins become catalog entries with their quirks. Settings > Providers gets "Add from ACP Registry" and "Add custom agent".

**B. Who implements `jetbrains.air`.** See [the table](#b-jetbrains-air-support-by-listed-agent).

- **Only three agents on the list implement AIR: Claude Agent and Codex (the two `agentclientprotocol` adapters) and Junie (JetBrains).**
  - Claude Agent and Codex document AIR in `docs/air-extensions.md`.
  - Junie's shipped jar contains:
    - `AirMeta`, with the `jetbrains` / `air` / `version` keys.
    - A `buildAgentMeta` that references `nativeSubagentSessions`, `agentFileChangeReport`, `planFile`, `customInstructions`, `unattendedInteraction`, `sessionIndexCapabilities` and `_session/goal`.
    - `clientSupportsSessionFailure`, which reads the client's AIR capability list.
  - A third-party recording of a Junie 26.11.3 `initialize` shows the advertised list `["nativeSubagentSessions","agentFileChangeReport","planFile","customInstructions","unattendedInteraction"]`.
- **No ACP SDK** (TypeScript, Python, Rust, Kotlin) contains AIR code, so no agent gets AIR by building on an SDK.
- **The other 45 of the 51 list entries show no AIR code**, nor does Grok Build (named inside the Cursor entry). The check covered the repo at HEAD or the shipped npm or binary artifact.
  - Cursor, Grok Build, Factory Droid, Augment, Kiro, Poolside, Command Code, and Imagera are closed source. Their shipped bundles were string-scanned and the scans found nothing.
- **Unknown: GitHub Copilot CLI, Blackbox AI, and stdio Bus.**
  - The Copilot CLI's Mach-O binary does not expose its JS.
  - The other Copilot ACP distribution, `@github/copilot-language-server --acp` (the one `registry-for-jetbrains-air.json` ships), is readable JS and has **no** AIR code.
  - Blackbox ships through an installer, and only a possibly stale npm 1.0.2 was checked.
  - The stdio Bus repo contains no agent source.
- **Practical upshot for hoa.** AIR-backed features (session index, archive/rename, `sessionFailure`, `recommendedValue`, `loadReplayEnd`) can only ever light up for Claude, Codex and, if added, Junie. A generic agent must work with the standard ACP surface alone.
  - Only `sessionArchive`/`sessionRename` are gated on what the agent advertises (`agentCapabilities.ts:104-123`).
  - `sessionIndex`, `sessionFailure`, `loadReplayEnd`, `recommendedValue` and `backgroundSubagents` are switched on by hoa's per-launch-target AIR offer (`PROVIDER_QUIRKS`, `declaresSessionIndex`, `agentCapabilities.ts:66-90`). So Junie would need its own quirk row, and an unknown AIR-capable agent never gets the offer.
  - Keep "no AIR offer" as the generic default: sending AIR identity alone changes adapter wire shapes (tool-call contract, subagent form; see the 11-18 note §Summary).

## A1. How hoa models providers today

### Identity: a closed union of four launch targets

- `AgentLaunchTarget = 'antigravity-acp' | 'claude-agent-acp' | 'codex-acp' | 'cursor-acp'` (`libs/ui/src/host/agentLaunchTarget.ts:9`). The glossary defines a launch target as "the spawn identity for a selectable harness connection": an adapter from a Provider runtime, a native Vendor CLI ACP process, or a Managed ACP Agent (`apps/desktop/GLOSSARY.md:298`).
- Beta gating is by compile-time env: `HOA_CURSOR_BETA` and `HOA_ANTIGRAVITY_BETA` (`agentLaunchTarget.ts:31-41`). Labels are a `switch` (`:46-57`).
- Persisted state is already string-keyed, so it is not the blocker:
  - `providerEnabled: Record<string, boolean>` (`libs/hoa-home/src/UserSettings.ts:24`).
  - `LaunchTarget` in hoa-home is a branded kebab-case string (`agentLaunchTarget.ts:59-61`).
- Exhaustive per-target tables that a dynamic id breaks:
  - `PROVIDER_QUIRKS: Record<AgentLaunchTarget, ProviderQuirks>`: AIR offer, Claude-SDK `_meta`, never-resume (`libs/ui/src/host/agentCapabilities.ts:51-85`).
  - `PROVIDER_META: Record<AgentLaunchTarget, ProviderMeta>`: label, CLI name, install hints, runtime kind, sign-in hint (`libs/ui/src/host/providerView.ts:70-119`).
  - `LAUNCH_TARGET_SVG` / `LAUNCH_TARGET_ICON_URL` (`libs/ui/src/components/AgentLaunchTargetIcon.tsx:11,18`).
  - `ImportState.targets: Record<AgentLaunchTarget, …>` (`libs/ui/src/host/importSessions.ts:31`).
  - Per-vendor `switch`es in `vendorCliAuth.ts:26-35,155-164` and `authMessages.ts:5-17`.
  - Partial tables that already tolerate absence: `providerCapabilities` (`libs/ui/src/components/sessionChat/configChips/providerCapabilities.ts:13-27`) and `HIDDEN_COMMAND_NAMES` (`…/composer/menu/filterAvailableCommands.ts:19`).
  - First-run defaults: `detectProviderEnabledDefaults` (`libs/ui/src/host/providerBootstrap.ts:9-18`).

### Three launch paths

`makeAcpLaunchCommand` dispatches on the target (`libs/ui/src/host/acpLaunchCommand.ts:128-157`):

| Path                                     | Targets                         | What runs                                                                                                                               | Prerequisites                                                                                                    | Source                                                                                                                          |
| ---------------------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **Node adapter from a managed runtime**  | `claude-agent-acp`, `codex-acp` | `node <runtime>/node_modules/@agentclientprotocol/<pkg>/…` with `CLAUDE_CODE_EXECUTABLE` / `CODEX_PATH` pointing at the PATH vendor CLI | `node` on PATH, an active runtime in `~/.hoa/providers/<id>/current.json`, vendor CLI on PATH, vendor auth probe | `acpLaunchCommand.ts:53-84,140-156`; packages `libs/hoa-home/src/providers.ts:19-22`                                            |
| **Native Vendor CLI**                    | `cursor-acp`                    | `cursor-agent [--api-key $CURSOR_API_KEY] [--auth-token $CURSOR_AUTH_TOKEN] acp`                                                        | `cursor-agent` on PATH, `cursor-agent status`-style auth probe                                                   | `acpLaunchCommand.ts:38-51,86-91`; `vendorCliAuth.ts:130-153`; ADR 0013                                                         |
| **Managed binary from the ACP Registry** | `antigravity-acp`               | the `cmd`/`args` recorded from registry `antigravity-acp/agent.json`, spawned by a Rust command that reads `current.json` itself        | an active runtime (downloaded archive, sha256-checked, origin-pinned to `dl.google.com/agy-extensions/`)         | `acpLaunchCommand.ts:93-125`; `antigravityRegistry.ts:9-80`; `apps/desktop/src-tauri/src/lib.rs:176`; ADR 0017 §Pinned metadata |

How the runtime-download path differs from Cursor's CLI path:

- **Runtime download** (Claude, Codex, Antigravity). This is user-initiated and backgrounded, with an explicit Install. It is cataloged in `current.json` with download states, pinned to an exact version, and re-read before every spawn (ADR 0017 §Decisions).
  - Claude/Codex still need the vendor CLI on PATH, because the adapter shells out to it.
  - Antigravity needs no CLI and signs in in-app through ACP `authenticate` (`libs/ui/src/host/backendHarness.ts:136`; `PROVIDER_META['antigravity-acp'].signIn = InApp`).
- **CLI path** (Cursor). No runtime, so `ProviderView.runtime` is `undefined` (`providerView.ts:64-65`). Status skips the runtime branch and goes straight from CLI-found to auth (`overallStatus`, `providerView.ts:143-179`).
- **Spawn permission differs too (desktop).**
  - The Tauri capability file allowlists `cursor-agent`, `claude`, `codex`, and `node` by name with `args: true` (`apps/desktop/src-tauri/capabilities/default.json:51-90`).
  - npm calls are pinned to regex-validated `@agentclientprotocol/(claude-agent-acp|codex-acp)` args (`:104-120`).
  - HTTP is restricted to `dl.google.com/agy-extensions/**` and the single Antigravity registry URL (`:38-45`).
  - Antigravity bypasses the shell plugin entirely through `spawn_antigravity_provider`, which "never accepts an executable path or arguments from the webview" (ADR 0017 §Native boundaries).

### Capabilities and quirks

- `agentCapabilitiesFrom` reads the `initialize` result once into a boolean record: `promptImage`, `promptEmbeddedContext`, `sessionClose`/`Fork`/`Resume`/`Delete`, `sessionArchive`/`Rename` (AIR), and `steeringSupported` (`agentCapabilities.ts:104-123`). `requireAgentCapability` refuses unsupported operations (`:164-177`). ADR 0013's amendment records that the Harness, not the launch target, now gates fork, archive, rename, and close.
- `supportsMcpHttp` reads `agentCapabilities.mcpCapabilities.http` (`agentCapabilities.ts:126-127`).
- `clientCapabilitiesFor` sends a fixed set for every target (`elicitation`, `session.configOptions.boolean`, `subagents`), plus the AIR offer only where `PROVIDER_QUIRKS[...].airClientCapabilities` is non-empty (`agentCapabilities.ts:148-156`). Cursor and Antigravity get no AIR offer (`:67, :84`).
- Auth:
  - `acpSessionBootstrap.ts` parses `authMethods` into `{ id, name? }` and drops `type`/`args`/`env` (`libs/ui/src/host/acpSessionBootstrap.ts:169-172, 473-490, 555`).
  - Launch-time auth is a vendor-specific CLI probe (`vendorCliAuth.ts:168-187`).

## A2. What a known-agent catalog entry needs (grounded in ACP)

Split by **where the fact comes from**. Only the first group must be stored; the rest is negotiated at runtime and must not be duplicated in the catalog.

**Static (catalog / registry manifest):**

| Field                                                                                    | Why                                                | Registry has it?                                                                                                                                                                                                      |
| ---------------------------------------------------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`, `name`, `description`, `icon`                                                      | picker, Settings                                   | yes. `icon` is a 16×16 monochrome `currentColor` SVG ([RFD §Icon requirements](https://agentclientprotocol.com/rfds/acp-agent-registry))                                                                              |
| launch: `cmd` + `args` + `env`                                                           | spawn                                              | yes, per distribution: `binary.<os-arch>.{archive,sha256?,cmd,args?,env?}`, `npx.{package,args?,env?}`, `uvx.{package,args?,env?}` ([FORMAT.md](https://github.com/agentclientprotocol/registry/blob/main/FORMAT.md)) |
| version + integrity                                                                      | pinning, offline launch (ADR 0017)                 | `version` (semver); `sha256` is optional per binary target (FORMAT.md §Archive integrity check)                                                                                                                       |
| PATH-CLI alternative (`cliName`, install hints)                                          | "use my installed CLI"                             | **no**. The registry describes only managed distributions. hoa's `PROVIDER_META.cliInstall`/`cliName` covers this                                                                                                     |
| hoa quirks (AIR offer, `claudeCode` `_meta`, never-resume, well-known config option ids) | adapter-specific behaviour not negotiable over ACP | **no**. These stay hoa-owned, keyed by registry id                                                                                                                                                                    |

**Negotiated at `initialize` (read, never configure):**

- `protocolVersion`; `agentInfo` / `clientInfo` (name, title, version) ([initialization](https://agentclientprotocol.com/protocol/v1/initialization)).
- `agentCapabilities`:
  - `loadSession`.
  - `promptCapabilities.{image,audio,embeddedContext}`. Text and `resource_link` are the baseline.
  - `mcpCapabilities.{http,sse}`. SSE is deprecated by MCP.
  - `auth.logout`.
  - `sessionCapabilities.{delete,additionalDirectories,systemPrompt,…}`.
  - Baseline: `session/new`, `session/prompt`, `session/cancel`, `session/update` ([initialization §Agent capabilities](https://agentclientprotocol.com/protocol/v1/initialization)).
- `authMethods[]`, each with `type`:
  - `agent` (the default when no type is given; the agent runs the flow itself on `authenticate`).
  - `terminal` (the client runs the same program with the method's `args`/`env` in an interactive terminal; only offered when the client declares `clientCapabilities.auth.terminal`).
  - The spec also defines `env_var`.
  - Clients MUST NOT pass a `terminal` method to `authenticate` ([authentication](https://agentclientprotocol.com/protocol/v1/authentication)).
- Extensions advertised in `_meta` (AIR, steering, …). The spec says extension keys SHOULD be reverse-DNS prefixed (`com.example/<name>`) ([extensibility](https://agentclientprotocol.com/protocol/v1/extensibility)). AIR's nested `jetbrains.air` does not follow that convention.

**Negotiated per session:** modes, models, and config options (`session/new` result `configOptions` / modes, [session-config-options](https://agentclientprotocol.com/protocol/v1/session-config-options), [session-modes](https://agentclientprotocol.com/protocol/v1/session-modes)), and available slash commands. Zed stores only user _defaults_ for these (`default_mode`, `default_config_options`, `favorite_config_option_values`), never the option list itself (`crates/settings_content/src/agent.rs:861-920` at `5a63e1a9`).

**Detecting an installed CLI** is not part of ACP or the registry. hoa's `requireExecutableOnPath` / `findExecutableOnPath` would apply to a custom agent's `command`. JetBrains says its IDE "can detect ACP-compatible agents already installed on your machine and offers to add them" but does not document how ([JetBrains ACP docs](https://www.jetbrains.com/help/ai-assistant/acp.html)).

## A3. Registries and prior art

### The ACP Registry (official)

- Proposed in [RFD "ACP Agent Registry"](https://agentclientprotocol.com/rfds/acp-agent-registry) (author @ignatov, champion @benbrandt) and announced as stabilized ([announcement](https://agentclientprotocol.com/announcements/acp-agent-registry-stabilized)).
- Repo: <https://github.com/agentclientprotocol/registry>, one `<id>/agent.json` per agent. CI validates the schema, icon, URL reachability, and an auth handshake. An hourly cron bumps versions from npm, PyPI, and GitHub releases ([README](https://github.com/agentclientprotocol/registry/blob/main/README.md)).
- **Published indexes** ([README §Usage](https://github.com/agentclientprotocol/registry/blob/main/README.md)):
  - `registry.json`, the general index.
  - `registry-for-jetbrains.json` and `registry-for-jetbrains-preview.json` (opt-in newest/preview channel).
  - `registry-for-jetbrains-air.json` ("intended for JetBrains Air and excludes Gemini CLI"). The live file has 45 agents vs 46 in `registry.json`: it drops `gemini` and lists `github-copilot` in place of `github-copilot-cli`. The AIR index is **not** a list of AIR-extension implementers.
- **Inclusion requires auth.** Agents must return at least one `authMethods` entry of type `agent` or `terminal` ([AUTHENTICATION.md](https://github.com/agentclientprotocol/registry/blob/main/AUTHENTICATION.md)).
- **Preview channel.** An agent may add `preview: { version, distribution }`, which only the JetBrains preview index serves. Preview builds are never launched or auth-checked by CI ([FORMAT.md §Preview Channel](https://github.com/agentclientprotocol/registry/blob/main/FORMAT.md)).
- **Quarantine.** `quarantine.json` lists entries currently broken (`agoragentic-acp`, `deepagents`, `minion-code`, `vtcode` as of `6f2077ce`).
- **Nightly protocol matrix.** `.protocol-matrix/latest.{json,md}` records per agent the init status, auth method types, `loadSession`/list/fork/resume capabilities, and probes of `session/list|fork|resume|stop|set_model`. In the 2026-11-23 run, 42 of 43 agents initialized and 27 returned `auth_required` on `session/new`. It does **not** record `_meta`. A client could use it to show "known capabilities" before the first launch.
- **Ids differ from hoa's:** registry `claude-acp` vs hoa `claude-agent-acp`, `cursor` vs `cursor-acp`. `codex-acp` and `antigravity-acp` match.
- **Cursor entry:** `binary` for all six OS/arch targets, `cmd: "./dist-package/cursor-agent"`, `args: ["acp"]`, no `sha256`, license `proprietary` (live `registry.json`, `version 2026.11.22`).

Clients consuming it:

- **Zed:** "The ACP Registry is the primary way to install common External Agents in Zed". Extension-provided agents are deprecated and auto-migrated to registry equivalents (Zed `docs/src/ai/external-agents.md` §Install from the ACP Registry, §Extension-Provided Agents).
- **JetBrains:** installs from the registry and "downloads and manages a Node.js or Python runtime if required" for `npx`/`uvx` entries. An org admin can restrict the list ([JetBrains ACP docs](https://www.jetbrains.com/help/ai-assistant/acp.html)).
- **Several desktop clients** on the [clients page](https://agentclientprotocol.com/get-started/clients) advertise "one-click agent install from the ACP Registry": Athas (Tauri), AcpAgent Client, littleguys, Zorvo (Tauri), Threadlines.

## A4. Risks and tradeoffs

- **Capability variance is wide** (registry matrix, 2026-11-23):
  - `cline`, `codebuddy-code`, `gemini`, and `stakpak` advertise only `loadSession`.
  - `kiro` and `corust-agent` advertise nothing beyond the baseline.
  - `session/fork` is supported by 14 of 43; `session/set_model` by 17.
  - hoa's Harness already gates on `AgentCapabilities`, so variance is handled where it matters. The gaps are the UI pieces keyed on provider id:
    - Config chips: `providerCapabilities` returns `undefined` for unknown ids, which is fine.
    - The model picker's well-known Fast/Plan option ids: Claude/Codex-specific.
    - Ultracode: Claude only.
- **Resume.** Cursor is forced to always `session/load` by a quirk, "until resume is proven" (ADR 0013). For unknown agents, the safe default is to trust `sessionCapabilities.resume` and fall back to `session/load` on error. Alternatively, default `neverResume: true` for custom agents. That is a product call.
- **Auth.** Per-vendor CLI probes don't generalize. Generic flow:
  1. Spawn and `initialize`, declaring `clientCapabilities.auth.terminal: true` only once a terminal UI exists.
  2. On `auth_required` from `session/new`, show `authMethods`:
     - `agent`: call `authenticate` (Antigravity already does).
     - `terminal`: run `command + method.args` with `method.env` in a PTY. The 2026-10-04 note covers the desktop PTY and VS Code terminal options.
     - `env_var`: prompt for the value and store it.
  3. The registry guarantees `agent` or `terminal` for listed agents. A custom agent may have none, so show the raw error.
- **Security (desktop).**
  - A user-defined command means the webview can name an executable. The current model allowlists names in `default.json` and keeps Antigravity's path native-only (ADR 0017 §Native boundaries).
  - Generic support needs a Rust spawn command that reads the agent definition from `~/.hoa` itself (as `spawn_antigravity_provider` reads `current.json`), so a compromised webview cannot pass arbitrary argv.
  - Registry archives need an origin and `sha256` policy. `sha256` is optional in the registry. Cursor's entry has none, while Antigravity's does.
  - The ACP [security page](https://agentclientprotocol.com/protocol/v1/security) and the terminal-auth launch-safety rule apply: pass `args` as an argv array and never build a shell line ([authentication §Launch safety](https://agentclientprotocol.com/protocol/v1/authentication)).
- **Managed runtimes for `npx`/`uvx`.** JetBrains downloads Node or Python as needed. hoa relies on a global Node ≥ 22 and npm (ADR 0017) and has no `uv`. `uvx` agents (`fast-agent`, `minion-code`) would need `uv` on PATH or be unsupported at first.
- **Registry drift.** The registry auto-bumps hourly. hoa's pinned-descriptor model (ADR 0017) already isolates launches from that drift. Keep it.
- **Pre-alpha:** no settings migration is needed (memory: pre-alpha scope). `providerEnabled` keys can be renamed (e.g. `cursor-acp` → `cursor`) freely.

## Proposed design (proposal)

> Proposal only. Not decided, and not an ADR.

### Data model

```ts
type AgentId = string & Brand<'AgentId'>; // kebab-case; registry ids reused verbatim when sourced from the registry

type AgentLaunch =
  | { _tag: 'Path'; command: string; args: readonly string[]; env: Record<string, string> } // CLI on PATH or absolute path
  | { _tag: 'Managed'; distribution: ProviderDistribution }; // pinned from registry: binary | npx (| uvx later)

type AgentDefinition = {
  id: AgentId;
  name: string;
  icon: { _tag: 'Builtin'; svg: string } | { _tag: 'Url'; url: string } | { _tag: 'None' };
  source: 'builtin' | 'registry' | 'custom';
  launch: AgentLaunch;
  quirks: ProviderQuirks; // today's PROVIDER_QUIRKS, default = DEFAULT_QUIRKS (no AIR offer, no claudeCode meta, trust resume)
  signInHint?: string; // free text; ACP authMethods drive the actual flow
};
```

- **Built-ins** (Claude, Codex, Antigravity, Cursor) become `source: 'builtin'` definitions in code. They keep their quirks, CLI probes, and `cliInstall` hints. Each one maps to a registry id (`claude-acp`, `codex-acp`, `antigravity-acp`, `cursor`) so that "Download" can use the registry descriptor.
- **Registry agents:** a user picks from `registry.json`. hoa pins the descriptor into `~/.hoa/providers/<id>/current.json` (the ADR 0017 flow, generalized from Antigravity) and stores `{ id, source: 'registry', env? }` in settings, matching Zed's `type: "registry"`.
- **Custom agents:** stored as `{ id, name, source: 'custom', launch: Path{command,args,env} }` in user settings, matching the Zed and JetBrains shapes.
- `AgentLaunchTarget` becomes `AgentId`. Each exhaustive `Record<AgentLaunchTarget, …>` becomes a lookup on `AgentDefinition` with defaults.

### UX outline

- **Settings > Providers:**
  - The existing rows (built-ins).
  - **Add agent ▸ From ACP Registry** (searchable list with icon, description, distribution type, and the matrix capability badges).
  - **Add agent ▸ Custom** (form: name, command with a file picker, args list, env key/value with secrets masked; then **Test connection**, which runs `initialize` and shows `agentInfo`, capabilities, and `authMethods`).
- **Status:** reuse `overallStatus`. `cli-missing` applies to `Path` launches, `needs-runtime`/`downloading` to `Managed`, and `not-signed-in` is driven by `auth_required` + `authMethods` instead of CLI probes for non-built-ins.
- **Gating:** everything already behind `requireAgentCapability` stays as is. Show "Not supported by <agent>" on hidden or disabled actions, as `AgentCapabilityMissing` already words it (`agentCapabilities.ts:164-177`).
- **Desktop spawn:** one Rust command, `spawn_agent(id)`, reads the definition (custom from settings, or registry/managed from `current.json`) natively. `cursor-agent`/`claude`/`codex` leave the shell allowlist over time.

### Suggested order

1. Make the id open: `AgentDefinition` table and default quirks, with the four built-ins as data.
2. Custom agents (`Path` launch) plus the generic `authMethods` flow (`agent` first, then `terminal` behind the PTY work).
3. Registry browse/install, generalizing `antigravityRegistry.ts` to any `binary`/`npx` entry.

## B. `jetbrains.air` support by listed agent

### Method and verdict criteria

What AIR is: the `initialize` result `_meta.jetbrains.air = { version, capabilities[], goal? }`, negotiated against the client's `clientCapabilities._meta.jetbrains.air.capabilities`. It also adds per-message `_meta.jetbrains.air.*` keys: `sessionFailure`, `agentFileChangeReport`, `recommendedValue`, `loadReplayEnd`, session-index row metadata, and `_session/*` extension methods. hoa's view is in `libs/ui/src/host/airMeta.ts`, `libs/ui/src/host/agentCapabilities.ts` and `libs/effect-acp/src/schema/sessionFailure.ts`. The full catalogue is in the [2026-11-18 note](./2026-11-18-acp-jetbrains-air-capabilities.md).

Verdicts count **agent-side** behaviour only:

- **yes**: the agent advertises `_meta.jetbrains.air` in `initialize`, or reads the client's `clientCapabilities._meta.jetbrains.air`.
- **partial**: the agent emits some AIR `_meta` keys without the negotiation.
- **no**: the inspected source or shipped artifact (which does contain ACP code) has no AIR code.
- **unknown**: nothing inspectable.

Code that only _consumes_ AIR (clients such as hermes-agent's desktop app) and forks of codex-acp do not count.

How each entry was checked (2026-11-23):

1. Every row of [get-started/agents](https://agentclientprotocol.com/get-started/agents) was mapped to its ACP implementation. `zed-industries/claude-agent-acp` redirects to `agentclientprotocol/claude-agent-acp`. `docker/cagent` redirects to `docker/docker-agent`. `block/goose` redirects to `aaif-goose/goose`. `sst/opencode` redirects to `anomalyco/opencode`.
2. **Open source:** shallow clone of the default branch (SHA below), then `rg -i 'jetbrains\.air|jetbrains\W{1,6}air\b|AirExtension|air[_-]extension|agentFileChangeReport|nativeSubagentSessions|"sessionFailure"|sessionFailure:'`. Every `jetbrains` hit was also reviewed. A clone is used instead of GitHub code search, which skips large files and non-default branches.
3. **Closed source, npm:** `npm pack --ignore-scripts <pkg>@<registry version>` (plus the `darwin-arm64` platform package where the CLI ships as a binary; Grok's `.br` was brotli-decompressed). Then `rg -a` with the same pattern. Nothing was executed. Each bundle was confirmed readable by finding ACP identifiers (`agentCapabilities`, `authMethods`) in it.
4. **Closed source, binary:** downloaded the registry `darwin-aarch64` archive and ran `rg -a` over the extracted tree. For Junie, `unzip`ped the `standalone/acp` classes from the jar and read their constant pools.
5. **Global leads:** `gh search code` for `agentFileChangeReport`, `nativeSubagentSessions` and `air-extensions`. All hits outside the three implementers were clients, forks or notes.

**Limits.**

- A string scan of a closed binary is weaker evidence than reading source. Minified identifiers are fine, but compressed or encrypted payloads are not readable (Copilot).
- The "no" rows describe the default-branch HEAD or the registry version on 2026-11-23 only.
