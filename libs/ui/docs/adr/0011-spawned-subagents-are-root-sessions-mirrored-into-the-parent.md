# A Spawned subagent session is a root session on its own launch target, mirrored into its parent's Subagent sessions

Issue #358 lets an agent start a child on any launch target through the Hub's `spawn_subagent`. The Subagent model assumed the child lives on the parent's launch target (`subagents` sits on one Backend harness snapshot, populated from the parent's own `subagent_spawned` updates), but a Codex child of a Claude parent talks to the Codex connection. The Prompt turn machinery (`beginPromptTurn`, `sendPromptTurn`, Prompt turn cancel, Config diffs) only works on an entry in that snapshot's `sessions` map, so the child is bound there as a root session on its own launch target (as Bind does: in the map, not a History entry), and a link recorded on the Harness routes its transcript, Pending interactions and Work state into the parent's launch target's `subagents`, which the Subagent view, Work state and Attention events already read. `SubagentSnapshot` gains its own `launchTarget` so cancel, replies and provider badges (#354) address the child's connection, not the parent's. #456 later allowed the parent's own launch target too: then the root entry and the mirror share one snapshot, so requests and updates for that id address the root entry, never the mirror.

## Considered options

- **Move `subagents` out of per-launch-target snapshots into one cross-target tree:** rejected; every reader (`subagentViewAtom`, `rootAncestorId`, the event fold) is per snapshot, and `Connection lost` resets state per launch target. A global tree would rewrite all of them for one feature.
- **Drive the child through raw `sendPrompt` and keep it only in the parent's `subagents`:** rejected; it skips the single Prompt turn lifecycle (atomic start, soft cancel, Attention event), so the Harness would maintain two turn implementations.

## Consequences

- The child exists in two places for the link's life: a root entry on its own target (drives the turn, receives its RPC responses) and a mirror in the parent's target. The root entry is the source of truth for the turn; the mirror is a view.
- A link is memory only. After a restart the child is not a Tracked session, so it is absent from Session History; the parent's replay still shows it as a Restored subagent, rebuilt from the Subagent result in its transcript (ADR 0013). After a restart the in-memory record is gone, so Import's `session/list` could list the child again; a durable parent→child store is deferred.
- Within an app run a Spawned subagent session is never listed in Session History or the Import list, live or after its link ends (#459); the Import rows are filtered by the same set. The hide key is the child's `(launchTarget, sessionId)` in a memory-only set of every child ever linked this app run, never pruned when a link ends; it is not a field on the History row, so rows from a `session/list` refresh are hidden too. Ending a link adds no History row; the transcript stays viewable from the parent's mirror.
- Two connection losses matter: the child's target (fails the child) and the parent's target (cancels and closes the children).
- A Spawned subagent session may target its parent's own launch target (#456). The root entry (`sessions`) and the mirror (`subagents`) are distinct maps keyed by distinct ids (the child's id is never the parent's), so they do not collide in one snapshot. The one place they could: live updates for a session id found in `subagents` are routed to a native Subagent's transcript, so that routing skips Spawned mirrors and lets the child's updates reach its root entry.
- **Telemetry links a child to its parent by id** (#454). The `startSpawnedSubagent` span carries the parent's `acp.session.id` and the child's `acp.session.child_id`; the child's Prompt turn spans and logs, and the spans and logs the turn correlates (session updates, permission and elicitation requests), carry `acp.session.parent_id`. `acp.launch_target` cannot do this job, since a child may run on its parent's launch target. Both are ids, so they follow root ADR 0002. The child's turn runs in the spawn's trace, but the attribute is what a query filters on. The config changes made while spawning and the cancel and close when the parent ends carry it too. Work a user starts on the child later (a cancel or config change) carries only the child's own `acp.session.id`; reach its parent through the spawn span's `acp.session.child_id`. The Hub's `hub.toolCall` spans for a child's calls carry `acp.session.parent_id` too: the child's credential is minted with its parent's id (`createSession`'s third argument) and the hub `bind` message passes it on, also when a hub restart re-binds it.
